1Motivation

Keyword search can't understand a shopping sentence

Bangladeshi e-commerce is fragmented across independent stores with no common search layer, and conventional search only matches literal words — not budget, brand, colour, or intent expressed together.

The worked example, from the proposal
"black backpack under 3000 taka with a laptop compartment"
Keyword searchmatches "backpack" only — budget, colour and the laptop-compartment requirement are silently ignored.
ShopMate AIparses category, colour, and budget as structured constraints, then ranks explainable results across every store.
Research Question

Can a conversational AI agent improve product discovery and purchasing efficiency across multiple Bangladeshi e-commerce platforms, compared with conventional keyword-based shopping?

No cross-store price comparison

The same product is listed under different titles on different stores — nothing identifies "the same item" automatically.

No bilingual understanding

Bangla and Banglish queries ("কালো ব্যাগ ৳3000 er moddhe") aren't understood by literal keyword matching at all.

No explainable ranking

A results list with no stated reason for ordering gives the shopper no basis to trust the recommendation.

2Architecture

A service-oriented split: business logic apart from AI

Laravel owns the schema, auth, and UI; FastAPI is a read-only AI service. Neither can corrupt the other's responsibility — and the AI layer can be swapped without touching the product.

4Engineering Judgement

Every simplification is documented and reversible

The proposal specified transformer embeddings, a vector database, and a learning-to-rank model. Each was deliberately substituted for a lighter equivalent — with the upgrade path written down, not abandoned.

Proposal componentThis buildWhy
Sentence embeddings + vector DBTF-IDF over MySQL, computed per requestCatalogue is tens–hundreds of products — a vector index is unnecessary weight at this scale.
Transformer intent classifierRule-based NLU, optional LLM APIZero-dependency baseline that starts instantly; LLM adds semantic generalisation only when configured.
Transformer product matchingToken-Jaccard + brand/model vetoesRuns instantly with no ML runtime; validated at 100% recall, zero false merges on real data.
Learning-to-rank modelWeighted multi-factor formulaExplainable by construction — every ranking has a stated reason, a proposal requirement.
Docker + Redis/CeleryPlain local processes, DB queueOne less moving part to run and debug on constrained hardware.
Documented in docs/IMPLEMENTATION_PLAN.md before implementation began — not a retrofit justification.
5Multi-Store Catalogue

One interface, three data sources, one matcher

A StoreProviderInterface abstracts where listings come from; every provider's raw listings pass through the same cross-store matching algorithm before reaching the database.

Why a model-code veto?

On real Othoba data, "Galaxy A17" and "Galaxy A07" scored above threshold on brand match + generic shared words ("galaxy", "ram", "rom") alone. A regex veto for letter-digit model codes fixed it without breaking the mock fixture's validated recall.

Why a stricter no-brand threshold?

Unbranded listings ("charging cable for X smart watch") share so much templated wording that 0.65 comfortably over-merges different products — 0.80 is required when neither listing names a brand.

6Natural Language Understanding

Rule-based by default, LLM-augmented by choice

A deterministic keyword/regex pipeline is the baseline — zero dependencies, instant, Bangla-aware. An optional LLM backend adds generalisation, with a hard requirement to fail safe.

"Sony headphones"LLM only

Recognised brand: "Sony" — a brand the hand-written keyword list never contained.

"phone"Corroborated

LLM says Smartphones; the word "phone" is a literal CATEGORY_SYNONYMS key — trusted without a relevance check.

"washing machine"Not corroborated

No synonym implies Home Appliances — held to a stricter per-candidate relevance floor before trusting it.

7Retrieval & Recommendation

Structured filters narrow it, TF-IDF and a weighted formula rank it

Category/brand/budget/rating act as hard filters over the catalogue; TF-IDF cosine similarity then scores textual relevance, feeding a five-factor weighted ranking with an explicit reason per result.

9Debugging Under Test

Diagnosing a "random results" defect

A real defect found, traced, and fixed during evaluation — shown because it demonstrates the actual failure mechanism, not just that a bug existed.

Two earlier fix attempts (reject the whole set; check raw substring overlap) each broke a different real query — "phone" and Bangla queries — before the synonym-corroboration design proved both correct and complication-free.

10Extending Coverage

"Not in the catalogue yet" isn't "not available"

A pre-imported catalogue only ever knows what it was told to fetch. When local search is genuinely empty, one on-demand live query closes the gap — and teaches the catalogue permanently.

11Responsible Automation

No automated purchase, ever

The proposal requires no bypass of authentication, CAPTCHA, or payment controls. "Buy" is a two-step, human-confirmed flow — not a checkout API call.

Step 1
Preview the real listing

Product photo (from Othoba's own public search response), brand, category, rating, and a direct link to the live store page — before any commitment.

Step 2
Confirm the order

Records the order in ShopMate's own database only — it never places, pays for, or automates anything on the store's own site.

No login, no CAPTCHA defeat, no payment automation — a deliberate architectural boundary, not a missing feature.

12Operations

Catalogue health is visible, not assumed

The matcher's decisions are auditable: a human-in-the-loop review queue for possible duplicates, per-store health, and demand signals from queries the catalogue couldn't answer.

14Closing

What this demonstrates, and what's next

Stated limitations
• TF-IDF, not true semantic embeddings — a documented upgrade path, not an oversight.
• Small held-out evaluation set (11 queries) — sufficient to prove methodology, not publication-scale.
• Single-item orders; no cart — a deliberate MVP scope cut.
• Mock catalogue plus one real live connector (Othoba) — the provider interface is built for more.
Future work
• sentence-transformer embeddings for true semantic retrieval
• Learning-to-rank personalisation from search/order history
• Additional real store connectors via the existing provider interface
Contribution

A working, end-to-end conversational shopping agent — bilingual NLU, cross-store semantic matching, explainable ranking, and human-confirmed purchasing — validated against a keyword baseline and hardened through real debugging on live data.

Every architectural simplification from the original proposal is documented, justified, and reversible.
